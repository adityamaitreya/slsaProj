## The Big Idea

We are building a **software supply chain security system**.

The question it answers is:

> **"Can I trust this software? Can I prove where it came from, who built it, and that nobody touched it?"**

Think of it like a food product. When you buy a jar of tomato sauce, the label tells you:
- What's inside (ingredients)
- Where it was made (factory)
- When it was made (date)
- That nobody tampered with it (sealed cap)

We are building the same thing — but for software.

---

## How the System Works (Simple View)

```
You write code
      ↓
Push to GitHub
      ↓
GitHub builds it automatically (trusted factory)
      ↓
Docker image created with a unique fingerprint (SHA-256)
      ↓
Ingredient list generated (SBOM)
      ↓
Build receipt generated (SLSA Provenance) ← coming next
      ↓
Everything signed cryptographically (Cosign) ← coming next
      ↓
Stored in database (PostgreSQL) or blockchain (IPFS)
      ↓
Anyone can verify: VALID / TAMPERED / INVALID
```

We have completed the **top 4 steps** so far.

### Stage A2 — Dockerization

**What it is:**
Packaging the Flask app into a Docker container so it runs the same way everywhere.

**Why we built it:**
Docker produces a **SHA-256 digest** — a unique fingerprint for the built image. This fingerprint is the foundation of our entire supply chain. If anyone changes even one byte in the code, the fingerprint changes. That is our tamper detection.

**What is a SHA-256 digest?**

```
sha256:5fbc20ebcfdd...
```

This is a 64-character hash generated by running a mathematical function over the entire contents of the Docker image. It is:
- **Unique** — no two different images produce the same hash
- **Deterministic** — same input always produces same hash
- **One-way** — you cannot reverse it to get the original image
- **Tamper-evident** — any change produces a completely different hash

**Multi-stage Dockerfile explained:**

```dockerfile
# STAGE 1: Builder
# Use a full Python image to install dependencies
FROM python:3.11-slim as builder
RUN pip install -r requirements.txt
COPY src/ ./src/

# STAGE 2: Runtime
# Use a minimal image — only copy what is needed to RUN the app
FROM python:3.11-slim as runtime
COPY --from=builder ...
USER appuser          # non-root user for security
CMD ["gunicorn", ...]  # production server
```

Why two stages?
- Stage 1 installs build tools and dependencies
- Stage 2 copies only the final result — no build tools, no clutter
- Result: smaller image (207MB), smaller attack surface

**Files created:**

| File | Purpose |
|---|---|

| `app/Dockerfile.dev` | Development build (hot reload) |

### Stage A3 — GitHub Actions CI/CD Pipeline

**What it is:**
Automation that runs every time code is pushed to GitHub. It builds the Docker image, runs tests, and pushes the result to a registry — all without any manual steps.

**Why we built it:**
This turns GitHub into our **trusted builder**. Instead of "I built this on my laptop," we can now prove "GitHub Actions built this from commit `abc123` at exactly this timestamp in this environment."

This is critical for supply chain security. Anyone can claim anything about software they built locally. But if a neutral, auditable system (GitHub Actions) did the build, we have real proof.

**Before vs After:**

```
Before:
  Developer laptop → Docker build → "Trust me, it's fine" ❌

After:
  GitHub Actions → Docker build → SHA-256 digest → Build log → Proof ✅
```

**What the pipeline does automatically on every push:**

```
Step 1: Checkout code
Step 2: Set up Docker Buildx
Step 3: Log in to GitHub Container Registry (GHCR)
Step 4: Extract metadata (tags, labels)
Step 5: Build and push Docker image
Step 6: Extract SHA-256 digest
Step 7: Generate SBOM (Stage A4 addition)
Step 8: Upload SBOM artifacts
Step 9: Upload digest artifact
Step 10: Create build summary
```

**What is GHCR?**
GitHub Container Registry — GitHub's own Docker image hosting. When GitHub Actions pushes an image here, it gets a registry digest:

```
ghcr.io/adityamaitreya/slsaProj@sha256:abc123...
```

This is different from the local image ID. The registry digest is the official supply chain fingerprint.

**Files created:**

| File | Purpose |
|---|---|
| `.github/workflows/build.yml` | Main CI/CD pipeline — build, push, SBOM |
| `.github/workflows/test.yml` | Test pipeline — pytest, flake8 |
| `.gitignore` | Files Git should ignore |
| `validate_github_setup.sh` | Script to confirm Stage A3 is ready |

**Key concept:**
The `id-token: write` permission in the workflow is already set. This is what allows GitHub Actions to generate SLSA provenance in Stage A5. We planned ahead for it.

### Stage A4 — SBOM Generation

**What it is:**
Automatically generating a Software Bill of Materials — a complete list of every library, package, and dependency inside the Docker image.

**Why we built it:**
You cannot secure what you cannot see. The SBOM tells us exactly what is inside the software. If a new vulnerability is announced (like Log4Shell in 2021), we can instantly check if our software is affected.

**What is an SBOM?**
Think of it as the ingredient label on food packaging.

```
Tomato Sauce Label:           Software SBOM:
- Tomatoes                    - Flask 3.0.0
- Salt                        - Gunicorn 21.2.0
- Olive oil                   - Werkzeug 3.0.1
- Basil                       - Python 3.11.16
- ...                         - openssl 3.x
                              - ... (~150-200 packages total)
```

**Three SBOM formats generated:**

| Format | Standard | Best For |
|---|---|---|
| SPDX JSON | ISO/IEC 5962:2021 — Linux Foundation | Government, compliance |
| CycloneDX JSON | OWASP standard | Security teams, vulnerability tracking |
| Syft JSON | Anchore format | Detailed metadata, Grype scanning |

We generate all three because different tools and organizations prefer different formats.

**How Syft works:**

```
Syft scans the Docker image by its SHA-256 digest
         ↓
Finds every installed package (Python, system, etc.)
         ↓
Generates structured SBOM files
         ↓
Uploads them as build artifacts (kept for 90 days)
```

Important: Syft scans by **digest**, not by tag. This means it scans the exact, immutable image — not a "latest" that could change.

**Files created/modified:**

| File | Purpose |
|---|---|
| `.github/workflows/build.yml` | Updated — added 4 new SBOM steps |
| `app/generate_sbom.sh` | Script to generate SBOM locally |
| `SBOM_GUIDE.md` | Complete SBOM documentation |

**What you can do with the SBOM:**

```bash
# Count all packages
jq '.artifacts | length' sbom.syft.json

# Find a specific package
jq '.artifacts[] | select(.name == "flask")' sbom.syft.json

# List all licenses
cat sbom.spdx.json | jq '.packages[].licenseConcluded'

# Scan for vulnerabilities
grype sbom:sbom.syft.json
```

## Technical Terms Explained

### `cat << 'EOF'`

This is called a **heredoc** (here document). It is a bash trick for printing multiple lines of text cleanly.

```bash
# Without heredoc (messy):
echo "Line 1"
echo "Line 2"
echo "Line 3"

# With heredoc (clean):
cat << 'EOF'
Line 1
Line 2
Line 3
EOF
```

The word `EOF` is just a marker that says "start printing here" and "stop printing here." You could use any word — `END`, `STOP`, `DONE` — but `EOF` (End Of File) is the convention.

The single quotes around `'EOF'` mean: print everything literally, do not try to expand variables like `$HOME` or `$USER`.

We use it to print formatted summaries after each stage completes.

### Why Multiple `.sh` Script Files?

Each script has one clear job. This is the **single responsibility principle** — one tool, one purpose.

| Script | When You Run It | What It Does |
|---|---|---|
| `app/run_dev.sh` | During coding | Starts Flask locally |
| `app/build.sh` | Before pushing | Builds and tests Docker image locally |
| `app/generate_sbom.sh` | When you want to inspect | Generates SBOM from local image |
| `validate_github_setup.sh` | Before pushing to GitHub | Checks everything is ready |

**Local scripts vs GitHub Actions:**

```
Local scripts (.sh files):
- Run on YOUR laptop
- You run them manually
- For development and testing
- Fast feedback

GitHub Actions (.github/workflows/*.yml):
- Run on GitHub's servers automatically
- Triggered by git push
- Trusted, auditable builds
- Creates provenance
```

They serve different purposes. The local scripts help you work faster. GitHub Actions creates the official, trusted artifacts.

## What Comes Next

### Stage A5 — SLSA Provenance

SLSA provenance is a cryptographic build receipt. It proves:
- **Who** built it → GitHub Actions
- **When** → exact timestamp
- **From what source** → exact repo + commit SHA
- **How** → exact workflow steps
- **What the result is** → SHA-256 digest

It is signed with a key so that nobody can forge or modify it after the fact.

### Stage A6 — Cosign Signing

Cosign digitally signs the Docker image and the provenance. If anyone tampers with either after signing, the signature verification will fail.

### Stages A7–A9 — Storage and Verification

This is where we build the actual comparison at the heart of the research:
- **System A (PostgreSQL):** Store provenance in a regular database
- **System B (Blockchain + IPFS):** Store provenance in a decentralized system
- **Verification API:** Same code, same logic, pluggable backend
